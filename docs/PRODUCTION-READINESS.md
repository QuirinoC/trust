# Trust production readiness plan

Updated 2026-09-25. This is a decision and verification plan, not a claim that the controls below are deployed. `STATUS.md` records observed release evidence; `DESIGN.md` remains the source for current UX. Trust's core promise is consensual, revocable location sharing. A feature that obscures consent, loses a paid entitlement, or implies a location or notification is current when it is not is a product failure as well as an operational failure.

## Sequence and release gates

| Gate | Work | Evidence required to pass |
| --- | --- | --- |
| 0 — complete the current beta | The real local-API simulator test of onboarding, invite, Off → Sealed → Off, and account cleanup passed. Next use two physical TestFlight accounts for SMS, background location, Look receipt, Pause, Stop, denial/reduced permission, airplane mode, relaunch, purchase, restore, expiry/refund, and deletion. Resolve the reported first-login Offline/Retry state. Reconcile App Store privacy/age answers and screenshots with the shipped binary. | Recorded build number, device/OS, account pair, steps, server state, screenshots/logs with private data redacted, and explicit pass/fail for each journey. Simulator and physical evidence remain distinct. |
| 1 — safe public launch | The current source batches location uploads in groups of at most 100 and removes a batch only after success. Protect queued coordinates on device and add retry-safe point IDs and queue bounds; make Look receipts retryable; make paid entitlements recoverable; instrument the API, app, database, SMS, APNs, and purchase flow; name an incident owner and backup; test alert delivery, rollback, and an isolated database restore. Define abuse handling and customer support procedures. | Reconnect and revocation tests; outbox/reconciliation tests; dashboard links and alert drill; measured restore time/data loss; signed-off incident, privacy, support, and release runbooks. |
| 2 — measured growth | Remove query and ingest bottlenecks, page history/activity, isolate background jobs, distribute rate limits, benchmark the real workload and its 3× peak, and add staging with migration compatibility checks. Scale the database and workers only from measured saturation. | Load-test report, query plans, cost per active connected pair, p95/p99 and freshness under peak, queue-drain test, rollback rehearsal. |
| 3 — large scale | Add database high availability and recovery capacity, partition or otherwise manage high-volume history, private object storage for photos if justified, separate analytics from the consent-serving path, and rehearsed regional disaster recovery. | Capacity and failover drills at the forecast active-sharer/update rate. A million registered accounts alone does not size the system. |

Do **not** postpone user-controlled Off, Pause, Stop, deletion, or access checks behind a subscription or operational upgrade. Do not describe APNs acceptance as delivery/display, or stale background coordinates as live.

## Concrete technical gaps and order

1. **Offline queue correctness.** The current source sends batches of at most 100 and removes each batch only after a successful response; the API limit remains in [`TrustEndpoints.cs`](../apps/trust-api/Api/V1/TrustEndpoints.cs). An ambiguous network response can still replay accepted points: add idempotent point identifiers, cap queue age/count/bytes, and test reconnect, restart, expired points, and sharing revocation. Move pending coordinates from plain `UserDefaults` JSON in [`LocationIngestStore.swift`](../apps/trust-ios/Sources/TrustApp/LocationIngestStore.swift) to protected local storage with an explicit deletion policy.
2. **Durable receipts and subscriptions.** A Look is stored before APNs is attempted inline, without a durable retry. Use a transactional outbox, bounded retry, invalid-token handling, and dead-letter triage. Store incoming App Store notifications with deduplication; replay unknown-owner events, reconcile with the App Store Server API, and model billing retry/grace, revocation, refund, restore, and out-of-order events. A paid-but-locked account must be diagnosable without support staff reading location history.
3. **Capacity hot paths.** The circle response performs per-person queries and loads Look records to count them; history has no paging; location points are inserted one at a time; each API replica starts a global minute sweeper; entitlement sweeping scans subscriptions. Batch/aggregate reads, keyset-page history and Activity, batch/idempotently ingest points, and give one leased worker ownership of each due cleanup/reconciliation job. Keep the latest location distinct from historical trails. Distribute rate limits across replicas. Profile before choosing caches or partitions; revocation checks must use authoritative state.
4. **Bounded external spend, SMS consent, and abuse.** The global SMS budget is currently 40/day, a beta limit rather than launch capacity. The pending app design uses the disclosed Send code button as the one-time-text confirmation, but the API currently records only the code request/challenge, not a durable consent event with the disclosure version and confirmation time; close that evidence gap before public release. The registered Twilio A2P campaign and `/sms` screenshot still describe the older separate control and must be reconciled with this flow before release. Configure country, phone/account/device/IP budgets and provider spend alarms, test HELP/STOP, and add an emergency stop that preserves sign-in alternatives/support. Define block/reinvite prevention, coercion and stalking reports, compromised-device session revocation, support escalation, and audited operator access. Avoid routine coordinate access in support tools.
5. **Runtime and release discipline.** Upgrade .NET 9 before its scheduled 2026-11-10 end of support. Use isolated staging credentials and data, backward-compatible migrations, versioned deploys, an explicit rollback point, and an on-call owner for each release. Validate the custom API hostname's TLS before pointing a client at it. Confirm the current TestFlight build is processed and assigned before interpreting a device test.

## The minimum operating cockpit

The targets below are **proposed initial objectives**, not measured performance or promises to customers. Review them after a beta baseline. Dashboards should show app version, release/deploy annotations, region, traffic, and sample size; charts must not include phone numbers, coordinates, names, invite codes, raw tokens, or other sensitive payloads.

| View | Signals | Initial action threshold |
| --- | --- | --- |
| API and database | Eligible request success, endpoint p50/p95/p99, 5xx/429, latency by version, connection pool, slow queries/locks, CPU, storage, migration and health results; authenticated no-SMS synthetic flow. | Proposed 99.9% 30-day request-success SLO and 99% of core reads under 1 second server-side. Page on sustained error-budget burn corroborated by synthetics at low traffic. |
| Location and consent | Ingest accept/reject/duplicate, local backlog age/count, age of latest permitted point by mode and permission, stale/empty map reads, revocation-check failures, retention-worker lag. | Page on any confirmed post-revocation access; investigate freshness regression and a stalled sweeper. Never infer freshness from a 200 response alone. |
| Notifications and SMS | Receipt recorded/queued/APNs-accepted, oldest outbox age, retry/dead-letter and invalid-token counts, SMS provider status/cost, verification completion and time-to-verify. | Proposed 99% first APNs attempts within 60 seconds; page if oldest queued receipt exceeds 5 minutes. Alert on abnormal SMS spend or conversion drop. |
| Mobile and revenue | Crash-free sessions, hangs, network errors by build/device/iOS, battery impact; verified entitlements, purchase/restore failures, notification lag, unmatched transactions, paid-but-locked cases, renewal/churn/refunds/net proceeds. | Proposed 99.9% crash-free sessions with count shown. Page on a growing entitlement-reconciliation backlog; investigate failed release cohorts. |
| Product and care | Onboarding → accepted connection → first consented share, weekly active connected pairs, D7/D30 retention, support volume/category and response time. | Use trends to decide UX/pricing work, not as paging alerts. Retain aggregate data under a written analytics policy. |

An initial tool stack can be small: one crash reporter, one metrics/logs/traces service, uptime/paging, a shared support inbox, and managed database backup/high availability. Prefer existing Render and Cloudflare capabilities where they meet the measured need; choose one provider per capability with telemetry retention/spend limits. Keep session replay off location screens. A status page becomes useful when incidents affect real customers. Record who receives alerts **and run a drill** before relying on any dashboard.

## Recovery, privacy, and ownership

- Confirm the live Postgres backup/PITR configuration, retention, encryption, access, and independent recovery path. Restore into an isolated environment, check that consent and deletion state are correct, and measure recovery. Proposed first targets: **RTO ≤4 hours**, **RPO ≤15 minutes**; these remain aspirational until a drill proves them.
- Give each severity an owner, backup, paging path, response window, rollback procedure, communication template, and post-incident review. Run one failure-injection exercise before public launch. Maintain a dependency inventory for Render, Postgres, Cloudflare, Twilio, Apple/APNs, and App Store billing.
- Document data classes and retention across app queue, API database, backups, logs, analytics, support tickets, and vendor systems. Restrict production access, audit sensitive actions, rotate/revoke credentials, and rehearse account deletion and export. Treat coercion and unwanted sharing as a product safety risk, with a clear user-report route.
- Complete the App Store age-policy, privacy answers, localized claims, terms and support review against actual behavior; confirm phone opt-in and STOP/HELP paths. Do not silently expand launch territories until SMS abuse controls and support coverage work there.

## Product and subscription decisions

Keep the existing **individual Plus** offer simple while measuring onboarding, connected-pair retention, purchase conversion, renewals, support complaints, and net proceeds. Free consent and safety controls stay usable. A household payer might remove the friction of every sharer buying Plus, but research it before adding a second SKU: determine who pays, who retains consent, who loses access on removal/downgrade, and how Apple Family Sharing interacts with the product. Never let the payer control someone else's consent.

Do not add a subscription-management vendor or Stripe just to appear production ready: native StoreKit already exists, while web billing is disabled. Add vendors only where reconciliation, support workload, or new platform distribution justifies cost and migration. Verify hardcoded website prices and trial claims against the live App Store by territory before public launch. Track unit economics per *active connected pair*: subscription net proceeds against SMS, maps/location storage, database, network egress, APNs operations, observability, support, and refunds. Model peak active sharers and update cadence, not only registered users.

For illustration only, **100,000 active sharers × 288 points/day = 28.8 million points/day**; at 30-day retention that is **864 million points** before indexes and replicas. Neither 100,000 sharers nor 288 points/day is a current Trust measurement. Benchmark real cadence and a reconnect storm before deciding partitioning, database size, or region strategy.

## Decisions for the owner

These need an explicit product/business choice, but do not block the local beta test work: public-launch age policy and countries; incident owner and backup; operating budget and acceptable RTO/RPO; retention/analytics policy; and whether Plus is intentionally individual for the first public release. The rest can be implemented and verified against those decisions.
