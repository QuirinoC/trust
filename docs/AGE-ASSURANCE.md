# Trust age assurance

Updated 28 September 2026. This records the current implementation and the unresolved product and jurisdiction decisions; it is not legal advice or a claim of global compliance.

## Current behavior

Trust no longer presents a global birth-date screen or applies a blanket 13+ access rule at launch. This follows the owner’s direction not to copy Life360’s child-account model or add age restrictions merely because a competitor does; implement age restrictions and consent steps only where law or Apple’s system requires them. The normal app asks Apple's Declared Age Range service only when Apple's regional eligibility or regulatory signals indicate that an age-related obligation applies. Age ranges stay in memory on the device. If a required Apple check cannot complete, access remains blocked for that Apple-signaled flow. Apple defines a `nil` lower bound as below the lowest requested gate; with Trust's lowest gate at 13, that response blocks account creation. It does not claim a parent-consent path is available. A declined request is represented separately; other incomplete or overlapping ranges remain restricted without labeling the person underage. A correction retry can request an updated Apple age range only while Apple currently signals that the person is in a region requiring age assurance; older systems without that signal retain the restriction and route to Support. Apple may replace the gates requested by an app with locally required age bands, so Trust's message refers to the returned range rather than asserting an exact age. In regions and OS versions where Apple does not signal that age assurance applies, the normal app does not ask a person's age or block sign-up based on age; a child may still attempt to create an account, and Trust currently has no parent-managed child account or first-use parental-consent flow. If Trust obtains actual knowledge that an under-13 user is using the service, the applicable COPPA response depends on its audience classification and may require stopping collection/deleting the account or implementing a compliant consent path. This Apple-signaled exclusion is not a global 13+ gate and is not a finished path for a child-directed or mixed-audience product. The age-range-required signal alone does not establish a universal 13+ account minimum.

On iOS 26.4 and later, the app follows Apple's per-person significant-update flags: Apple's adult acknowledgement when required and PermissionKit parental approval when required. On iOS 26.2–26.3, the app combines Apple's eligible-region signal with the shared age range; a known minor in an eligible region receives the PermissionKit parent-approval flow for the current significant update. Trust checks the verified StoreKit App Transaction's `originalAppVersion` against the `CFBundleVersion` build number that introduced the change; on iOS, Apple's property contains the original build number, not `MARKETING_VERSION`. The current threshold is build 33, matching `CURRENT_PROJECT_VERSION`; bump it alongside `significantUpdateID` for each new significant change. An install whose original build is 33 or later is treated as having installed with the change already present and is not asked to acknowledge it retroactively; an earlier original build follows Apple's significant-update flow. If StoreKit cannot provide a verified transaction, Trust retains the conservative existing flow. Apple's Sandbox `originalAppVersion` is always `1.0`, so the new-install exemption cannot be validated with Sandbox/TestFlight installs; it requires a production App Store transaction. This follows Apple's current guidance and avoids the deprecated `significantAppChangeApprovalRequired` property. The active PermissionQuestion and its stable ID are stored locally so a response can still be matched after backgrounding or process relaunch; the approved update ID is stored in Apple's iCloud Key-Value Store for both adult and parental acknowledgements. Each detected rating-transition occurrence receives a unique acknowledgement ID; Trust persists an unresolved transition marker (ID, previous code, and target code) independently of its PermissionQuestion and signed-in session, then reuses it across reevaluations or relaunch. Denial and account/session cleanup clear only question/response state and cannot erase that marker; it remains blocking when StoreKit returns no usable rating, until the same transition is approved or a usable rating shows it no longer applies. A later occurrence of the same code transition gets a new ID. The pending record also stores whether that prompt covers the current significant update, so relaunch restores accurate copy. Trust mentions and records the release acknowledgement only when that release change still applies and remains unacknowledged; otherwise the prompt describes the rating change alone. If StoreKit temporarily returns no usable rating while a transition is pending, Trust retains that pending decision and keeps access restricted until the rating is available or its acknowledgement has completed. Trust advances the stored rating baseline only after the required approval or acknowledgement, so a repeated transition cannot reuse an earlier approval. After a response, Trust reevaluates Apple's current age and regulatory signals before reopening the authenticated app. If the acknowledgement cannot be synchronized or read back, the app fails closed for that required flow. A new update ID requires a new decision, and a pending response for an older update is discarded. When Foundation reports an iCloud account change, the app immediately suspends age access and location tracking, invalidates in-flight account operations, clears pre-authentication age decisions held in the device Keychain, and reevaluates the new Apple Account before restoring the authenticated surface. A server privacy hold is different: it is attached to an authenticated Trust account and remains in force across Apple Account changes. The app preserves a token-fingerprinted, deletion-only session marker for that held Trust account, restoring the delete/support screen before age or StoreKit startup. It also reevaluates when returning to the foreground to catch changes made while the app was backgrounded. On iOS 26.0–26.1, the regional eligibility signal is unavailable to this implementation, so it proceeds without inferring a global requirement. This creates an unresolved pre-26.2 and jurisdiction-specific coverage gap. The app transaction is used to map Apple's consent-revocation notification to Trust accounts; it does not prove age.

On iOS 26.2 and later, the app also reads `AppStore.ageRatingCode` when available and compares positive codes with the last known code. StoreKit codes are treated as opaque: Trust does not infer an age from a code or send it to the API. In a region where age assurance is required, a changed rating now requires PermissionKit approval when Apple's shared age range proves the person is a minor; a known adult follows Apple's adult-notification flag, and an ambiguous range keeps access restricted. This follows Apple's guidance to request parent or guardian consent after an app-rating change for a child. Outside a regulated region, a rating change alone does not create an age prompt. The positive code baseline is retained in iCloud Key-Value Store and the device-only Keychain so reinstalling does not silently discard the previous rating. Each rating occurrence has its own policy-scoped transition ID. An acknowledgement also records the current release ID only when the prompt described that still-pending release change; the changed rating is saved only after approval. Bump `significantUpdateID` when shipping a new material age-related change so an old approval cannot carry forward. The value `0` returned by Xcode/Sandbox/TestFlight is ignored and is never saved as a baseline. See [Apple's StoreKit property documentation](https://developer.apple.com/documentation/storekit/appstore/ageratingcode), [Apple's age-range implementation guide](https://developer.apple.com/documentation/declaredagerange/requesting-people-share-their-age-range-with-your-app), and [age-assurance Q&A](https://developer.apple.com/support/age-assurance).

The `TRUST_AGE_TEST_MODE` path and the debug-only age UI tests exercise legacy local decision screens as controlled fixtures. They are not used by normal launch. Release behavior is governed by `AgeAssuranceCoordinator.evaluate` and Apple's signals. An Apple response below the lowest applicable gate leaves a device-only Keychain block; resetting app preferences does not remove it, but an Apple Account change clears it before the new account is evaluated. Age-evaluation and authenticated-startup continuations carry generations so a delayed response from a previous Apple account cannot overwrite the current access decision or reveal cached account data.

Before loading an authenticated account's circle or location data, the app registers its signed StoreKit App Transaction with the API. The API now independently blocks ordinary authenticated routes until it has verified and linked an App Transaction; transaction registration, account deletion, and push-device removal stay reachable so setup and cleanup can complete. If StoreKit verification or registration fails, the signed-in app stays at a retry screen; it no longer continues with an unlinked account. This lets Apple's later revocation notice be mapped to Trust accounts. It does **not** prove age or initial parental consent. When Apple's App Store Server Notification reports consent revocation, the API fails closed for the linked account while deletion is pending. The block applies to both the revoked account and connected viewers trying to read it: circle/profile data, history, snapshots, and avatar photos are unavailable, and the account cannot send new location data or receive push alerts. Home-arrival fan-out rechecks the subject's revocation state before sending to each recipient and each device. The iOS client now immediately clears the current account, disk cache, open snapshots, and history when any authenticated request reports `consent_revoked`; a response tied to an older account token cannot clear a newer session. A background worker now retries deletion for accounts that remain durably blocked after a transient failure, independently of another Apple notification or client request. Retry jobs persist in Postgres, use expiring per-item leases across API replicas, and back off exponentially after failure so a repeatedly failing batch cannot starve later deletions. Migration 017 backfills accounts already pending cleanup, including accounts registered after revocation. This revocation/deletion protection is implemented; it is not an initial parent-consent grant system.

Current verification and remaining test limits are listed in [Verification and evidence](#verification-and-evidence) below.

An account-level privacy hold does not automatically delete the account. While ordinary access is blocked, the affected person can choose self-service account deletion from the hold screen; the app asks for confirmation, calls the existing account-deletion endpoint, and signs out after success. Deletion removes the hold along with the account. On acknowledgement, the client retains only the current authenticated session required by the server's deletion exception, and persists a token fingerprint in Keychain so relaunch restores the delete/support screen before normal Apple-age or StoreKit checks. All other held-account API operations remain blocked. The local API simulator test applies a hold, verifies ordinary access is denied, restarts without test sign-in flags, deletes the held account, and confirms a new session is issued. This is a user-requested deletion option, not an automatic COPPA response or an initial parental-consent flow.

## Product and legal questions still open

Trust's audience classification under COPPA has not been resolved. A general-audience service may choose to block under-13 visitors and does not have to ask everyone's age; once it has actual knowledge of an under-13 user, it must either comply with COPPA or delete that user's information. A child-directed service cannot use an age screen to block children. A mixed-audience service may age-screen before collecting personal information, but it must provide a compliant path for identified children rather than treating 13+ as its finished child-protection design. Precise geolocation is COPPA personal information, and collection itself triggers the obligation even if the app does not use or disclose the coordinates. Counsel must assess Trust's actual audience, family positioning, visual design, location features, and launch markets before release. Do not expand the account model for under-13 users without a separate product and counsel design for guardian ownership, consent, account recovery, sharing defaults, and deletion. [FTC COPPA FAQs](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions).

Apple App Store classification is a separate decision from COPPA. Starting September 2026, App Store Connect requires every submission to declare whether the app has social media capabilities. Apple defines this as redistributing, amplifying, or interacting with user-generated content through a social feed or similar discovery method. Trust's current design is private person-to-person discovery and consent-based location sharing; it has no public feed or broad content-discovery surface, so it appears not to meet Apple's social-media definition. Recheck the shipped feature set before each submission and answer the App Store questionnaire accurately. Apple's current global age-rating table places both the Social Media and Social Media Disabled for Users Under 13 descriptors in the 13+ rating category; the disabled-under-13 descriptor also requires checking age through Declared Age Range before enabling those features. Apple's separate Time Allowance rule says a social-media capability disabled for users under 13 is excluded from the Social Media allowance category for those users. These are App Store classification and feature-control rules; they do not by themselves create a legal 13+ account minimum for Trust, and an App Store rating can be overridden by a parent in Screen Time. See [Apple's current submission guidance](https://developer.apple.com/news/?id=tlur8uvi), [age-rating definitions](https://developer.apple.com/help/app-store-connect/reference/app-information/age-ratings-values-and-definitions), and [Apple's age-assurance Q&A](https://developer.apple.com/support/age-assurance).

Apple provides Declared Age Range worldwide, but outside regulated regions the person or guardian can choose whether to share it. Apple says developers remain responsible for age restrictions and legally required significant-update controls. In a regulated region, the system can override the gates the app requested and return its local age categories; outside those regions, the returned bands use the app's requested gates. The request supplies 13, 16, and 18, matching Texas's statutory child, younger-teen, older-teen, and adult boundaries; Apple can replace these with jurisdiction-required bands. Trust derives a coarse age-band enum only in memory and never stores or transmits the raw range or band. The age-band mapping is tested against the inclusive 0–12, 13–15, 16–17, and 18+ boundaries. Per Apple's API contract, a `nil` lower bound means the person falls below the lowest requested gate; because Trust's lowest gate is 13, that response is under 13 and the current account-creation flow blocks it. A declined request is a separate result, and an incomplete or overlapping non-nil range stays restricted until resolved. On iOS 26.2–26.3, Trust uses the eligibility signal plus the shared range to identify minors for significant-update parental approval, following Apple's current guidance; on iOS 26.4+, it follows `requiredRegulatoryFeatures`. Availability of the API is not evidence that a particular region requires a check, and an App Store age rating is not a substitute for a required flow. The exact jurisdictional obligations and the behavior required on pre-iOS-26.2 systems remain to be established with counsel. No global legal-clearance claim is made. See [Apple's age-range request guidance](https://developer.apple.com/documentation/declaredagerange/requesting-people-share-their-age-range-with-your-app).

The current iOS deployment target is 18.0, while Apple's regional eligibility signal requires iOS 26.2 or later. On iOS 18–25, the app has no Declared Age Range framework; on iOS 26.0–26.1, it can request a range but cannot determine Apple's regional eligibility signal. Trust currently lets these devices continue without a region-specific age check. That coverage is **not verified for users subject to an applicable regional law**. This matters for California AB 1043/AB 1856, whose age-signal duty begins 1 January 2027 and requires a signal when the app is downloaded and launched; existing installs have a 1 July 2027 catch-up date. Trust must not add a global date-of-birth prompt or ask Apple for an age signal where no law requires it. Before launch in jurisdictions with those duties, counsel and Apple must confirm the supported OS/device policy or a lawful alternate signal; if no supported path exists, restrict availability on unsupported OS versions in the affected market. A StoreKit age rating is not a user-age signal.

### U.S. jurisdiction watch (checked 28 September 2026)

Do not use the superseded 2025 Apple announcement that paused Texas support. Apple announced on 3 June 2026 that new Apple Accounts in Texas became subject to SB 2420 starting 4 June after the Fifth Circuit stayed the injunction; the U.S. Supreme Court denied the application to vacate that stay on 6 July. Texas Business & Commerce Code §121.054 requires each app developer to use app-store-provided information to verify every user's age category and, for each minor, whether app-store consent was obtained; §121.055 limits how that data may be used and requires deletion after verification. Apple directs developers to use Declared Age Range, PermissionKit, `AppStore.ageRatingCode`, and App Store Server Notifications. The published Declared Age Range model exposes the age range, how it was set, and parental-control information; Apple's server-notification guidance describes `RESCIND_CONSENT` for withdrawal. I found no documented positive, current app-specific consent-grant field in these interfaces. A guardian-declared age range is not itself proof of consent to Trust's download or data use, and absence of a revocation is not proof of a grant. Trust reads age-range and significant-change signals and has a revocation endpoint, but has not validated the end-to-end mapping for initial minor consent in Apple's Sandbox; the backend records revocation, not a current consent grant. Do not call this production-ready until Apple confirms the developer-visible consent evidence and it is validated in Sandbox, and the API migrations and server-notification configuration are deployed. [Texas Business & Commerce Code, Chapter 121](https://tcss.legis.texas.gov/resources/BC/htm/BC.121.v3.htm), [Apple's current Texas notice](https://developer.apple.com/news/?id=sg176nne), [Apple's Declared Age Range API guide](https://developer.apple.com/documentation/declaredagerange/requesting-people-share-their-age-range-with-your-app), [Apple's revocation/Sandbox guidance](https://developer.apple.com/documentation/storekit/testing-age-assurance-in-sandbox), [Fifth Circuit order](https://www.ca5.uscourts.gov/opinions/pub/26/26-50001-CV0.pdf), [Supreme Court docket](https://www.supremecourt.gov/docket/docketfiles/html/public/25a1389.html).

California's Digital Age Assurance Act (AB 1043) becomes operative on 1 January 2027, with existing users covered by a 1 July 2027 catch-up date. As amended by AB 1856, it calls for an age-bracket signal at download and launch, treats a received signal as actual knowledge across the developer's platforms and access points, permits periodic compliance checks without requiring a prompt at every login, and prohibits requesting an age signal when the Act or another applicable law does not require it. The Act also bars prompting users to change their age information. Do not add a California-only birth-date prompt or routine age re-prompt. Before the effective date, verify how Apple's system signal will identify California applicability and how a received iOS signal is enforced across Trust's API and any future web account path. [AB 1043](https://leginfo.legislature.ca.gov/faces/billTextClient.xhtml?bill_id=202520260AB1043), [AB 1856](https://leginfo.legislature.ca.gov/faces/billNavClient.xhtml?bill_id=202520260AB1856).

Utah's amended developer requirements begin 6 May 2027. They include age-category and parental-consent status requests, notice to app stores of significant changes, restrictions on terms enforcement against minors without verified consent, and age-appropriate defaults. Louisiana repealed the 2025 Act 481 before it took effect; the replacement 2026 Act 185's main requirements start 1 July 2027. Louisiana expressly defines a “family account application” and lets such an app use the primary account holder's age category for safety defaults and allow that account holder to attest to associated subaccount ages, while retaining the other developer duties. Counsel should decide whether Trust qualifies and what evidence/consent rules still apply. These are future build requirements, not reasons to impose a blanket 13+ gate today. [Utah Code, Chapter 76](https://le.utah.gov/xcode/Title13/Chapter76/C13-76-P2_2026050620250507.pdf), [Louisiana Act 185](https://www.legis.la.gov/legis/ViewDocument.aspx?d=1471343), [Louisiana bill status](https://www.legis.la.gov/Legis/BillInfo.aspx?i=251085).

## Required gates before supporting under-13 accounts

Do not treat Apple's significant-update approval as consent to collect a child's data at first use. If counsel decides Trust must support under-13 users, implementation needs an adult-owned/dependent profile path before child account data or precise location is collected. The parent must receive a direct notice describing collection, use, family-circle disclosure, processors, retention, and control rights; Trust needs a counsel-approved verifiable-parental-consent method and a persisted consent record scoped to the child and disclosure purpose. A phone OTP verifies number access only. A verification provider must be selected before building identity/consent integration; do not capture government ID, face images, or payment data ourselves as a shortcut.

Enforce the resulting policy on both client and API. Before valid parent consent, prevent child account creation, SMS verification, precise location upload, profile disclosure, push registration, and circle membership. After consent, default every location share off; let the parent review the child's collected data, disable further collection/disclosure, request deletion, and withdraw consent. A withdrawal must immediately block authenticated data access and location ingestion, stop outbound notifications/sharing, and make account/data deletion retryable. Store the minimum consent evidence required by counsel; never retain a child's full birth date or identity documents unless the selected legal method requires it and counsel approves the retention.

Release test matrix must cover: each returned age band, no shared range, failed Apple checks, required Apple checks on iOS 26.2+, and unsupported iOS 18–26.1; child sign-up attempts without consent (including direct API requests); rejected, abandoned, verified, and withdrawn parental consent; no location, SMS, push, or profile data before consent; explicit Off-by-default share behavior after approval; parent review/export/delete; significant-update adult and parent branches; Apple's `RESCIND_CONSENT`; retries after partial deletion; and switching the guardian's Apple account. None of the under-13 cases can be considered verified until the jurisdiction/audience decisions and consent mechanism are selected and exercised in Apple's Sandbox and the real API.

## Comparator: Life360

Life360 chooses to support child and teen accounts; the law does not generally require a service to offer accounts to children. Its current Terms (last updated 24 August 2026) tell users under 18 to have a parent or guardian read and accept the Terms and require explicit parental consent before a child under 13 creates an account. Its Privacy Policy says a parent can add a child, that children may use most Life360 features, and that Life360 does not knowingly collect from under-13s (or users below a higher local consent age) without consent where required. It says Life360 does not show ads in child/teen accounts and does not share or sell information from members it knows to be under 18, while profile and location sharing inside a Circle remains available. In limited circumstances, Life360 may use an identity-verification vendor that processes government ID and a selfie, potentially with facial-recognition technology, to verify age or parental consent. Those are Life360's product and compliance choices, not proof that every location-sharing app must serve under-13s or collect government ID. See [Life360 Terms](https://legal.corp.life360.com/hc/en-us/articles/16124856472471-Life360-Terms-of-Service), [Life360 Privacy Policy](https://legal.corp.life360.com/hc/en-us/articles/16038777217175-Life360-Privacy-Policy), and [Life360's identity-verification notice](https://legal.corp.life360.com/hc/en-us/articles/16043932610967-Identity-Verification).

Life360 is not legally required to copy its exact model. Its under-18 parental Terms rule is broader than COPPA's under-13 trigger; local laws may impose different thresholds or duties, and Life360 has chosen a child-support path with stricter safeguards. Trust could choose a general-audience exclusion only if its actual targeting and product fit that classification. Trust's current published legal copy no longer claims this classification is settled; the brand and product aim at households and families, prior ad concepts depict children, and children may install Trust to share location. Those facts make an unsupported classification risky, and counsel should assess the shipped flows and actual marketing. If Trust targets children as one audience, a 13+ hard block is not the completed path; if Trust remains general audience, an under-13 block is legally available but not mandatory as an age screen. A phone OTP proves access to a number, and Apple's age-range result communicates an age category plus how that age range was declared or confirmed; neither alone verifies that an adult consented to Trust's collection and disclosure of the child's location to circle members. In particular, Apple's `guardianDeclared` age-range source is not itself a Trust consent record, and Apple's `RESCIND_CONSENT` server notification is a withdrawal signal rather than an initial grant record. The iOS SDK has no separate initial per-app consent-status property. Validate with Apple in Sandbox how the required app-store consent status is exposed before treating the initial grant path as complete. Where COPPA verifiable parental consent is required, use a method reasonably designed to establish that the consenting person is the child's parent and clearly cover Trust's location disclosures to circle members. See the [FTC COPPA FAQs](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions), [Apple's age-assurance Q&A](https://developer.apple.com/support/age-assurance), and [Apple's age-range declaration documentation](https://developer.apple.com/documentation/declaredagerange/agerangeservice/agerangedeclaration).

The FTC does not prescribe one parental-consent method; the operator must choose a method reasonably designed to ensure the person consenting is the child's parent. Its February 2026 policy statement gives limited enforcement discretion for collecting, using, and disclosing age-verification data solely to determine a user's age, if notice, purpose limitation, deletion, security, vendor, and accuracy conditions are met. That policy does not replace verifiable parental consent for subsequently collecting or disclosing a known child's location. The FTC currently lists PRIVO and kidSAFE among its approved COPPA Safe Harbor organizations. PRIVO publishes parent/child registration, feature-specific consent APIs, and a native Swift SDK; its developer docs require partner credentials. Kids Web Services (KWS) says its parent verification and consent service is certified by the ESRB and kidSAFE Safe Harbor programs, but this review did not find equivalent public native-iOS integration documentation. **Shortlist, not a vendor selection:** evaluate PRIVO first for the documented Swift SDK and consent/status APIs, with KWS as an alternative if its product and integration fit Trust's needs. A Safe Harbor listing/certification is not a blanket guarantee that Trust's use complies. Before selection, confirm the exact VPC method, whether it covers Trust's precise-location disclosure to circle members, parent review/deletion/withdrawal hooks, device/account model, data returned/retained, contract, and price with the vendor and counsel. No vendor is integrated and no child data has been sent. See [FTC parental-consent methods](https://www.ftc.gov/business-guidance/privacy-security/verifiable-parental-consent-childrens-online-privacy-rule), [FTC's 2026 age-verification policy](https://www.ftc.gov/news-events/news/press-releases/2026/02/ftc-issues-coppa-policy-statement-incentivize-use-age-verification-technologies-protect-children), [the current Safe Harbor list](https://www.ftc.gov/enforcement/coppa-safe-harbor-program), [PRIVO's Swift SDK](https://developer.privo.com/mobile/swift-usage.html), [PRIVO's parent/child registration API](https://developer.privo.com/api-rest/acc-register-user.html), and [KWS's parent-verification explanation](https://support.kidswebservices.com/).

- When Apple returns an under-minimum age range for an already signed-in Trust account, the app immediately restricts its local data and location behavior, then submits an authenticated privacy-hold request for that same account. The request contains no age range or client-selected account/reason. The API can only record that the client reported a restriction; it cannot independently verify Apple's result. The server hold is established only after the API acknowledges the request. If the device is offline, local access stays restricted, but the server has not acknowledged protection yet. A hold is separate from consent revocation and does not delete the account; only explicit account deletion removes the hold. There is no self-service clearance or automatic clearance after relinking/reinstall. Recovery/retention policy needs counsel and support review; any manual clearance must explicitly reset effective location-sharing permissions to Off before reactivation. The current client offers a support path for held accounts.
