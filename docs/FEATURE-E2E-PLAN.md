## Cross-device implementation follow-up — 2026-09-29

Astra reviewed the multi-device mutation and read paths and found two races. A circle GET started before Stop/Remove could finish later and overwrite the acknowledged result; rapid mode/Pause submissions could reuse an old revision and leave the user's latest choice unapplied. Circle reads now pass a generation barrier before updating memory or disk, and a stale read queues a fresh request. Per-connection writes serialize consent-enabling changes while Off remains available. A stale Look response cannot dismiss a newer confirmation sheet.

Swift tests cover the generation barrier, per-connection mutation gate, connection-scoped local mutations, stale request ownership, and cached Stop/Pause/Remove transformations; release HEAD `637b809` passes **82/82** TrustCore tests. Current CI run `36793168979` passed all jobs; its iOS UI target ran 28 tests, with 19 passing and 9 real-API tests skipped because no isolated API URL was configured. The latest local iOS simulator suite passed 101 tests with the same 9 real-API cases skipped. Xcode 27.1 beta generic Simulator `build-for-testing` succeeds. The paired iPhone 17 Pro + Duo lifecycle suite and the separate History UI regression passed on the 29 September checkpoint, and focused proxy tests cover delayed Circle reads and failed reconciliation across Stop/Remove, partial Stop All failure/retry, and delayed Look during remove/re-add. Delayed History remains untested because this isolated lane cannot establish a legitimate Plus entitlement; same-account second-device behavior, offline/reconnect, and physical-device behavior remain open. See [LOCAL-TWO-ACCOUNT-E2E.md](LOCAL-TWO-ACCOUNT-E2E.md) for evidence and limitations.

## Coverage targets and remaining acceptance

- Automated API coverage should include request add/cancel/decline/accept/re-add; reciprocal Off/Sealed/Always modes; Pause/Stop; fresh versus stale/denied/revoked location; Free/Plus history bounds and invalidation; Home set/update/clear and manual status independence; Look receipt persistence versus APNs publish attempts; arrival grants, Hidden, and removal.
- Swift regressions should prove stale account operations cannot mutate current sharing/history state and should exercise significant async response races. UI evidence should remain separate from helper/API evidence.
- The role-based paired UI test is `testPairedRequestAcceptAndPresenceGrantRole` in `TrustRealAPIFeatureTests`. The latest pass is `/tmp/trust-pair-alice-agefix-20260929.xcresult` and `/tmp/trust-pair-bob-agefix-20260929.xcresult` (1/1 each). Both simulator apps performed reciprocal Home/Away grants through their native UIs, including Bob's grant through Duo. The run also covered phone invite/accept, Home movement/update/clear, Hidden suppression, Look/map/Activity, Stop/removal/re-add, matching fresh connection IDs, and default-Off after re-add. This is Development + Memory simulator evidence with fictional phone fixtures, not physical SMS or APNs evidence. The safe paired-run setup and result details are in [LOCAL-TWO-ACCOUNT-E2E.md](LOCAL-TWO-ACCOUNT-E2E.md).
- Sharing includes a per-person, default-off Home/Away presence grant. Presence appears only when that grant is enabled and the viewer's current inbound location permission is effective; Off/Pause suppress it, Hidden is never shown, and removing the connection revokes the pair. Grant creation is rejected after removal and serialized against revocation. Location coordinates remain governed by the separate sharing mode.
- Completed focused race evidence: delayed Circle reads and failed reconciliation reads across Stop and Remove, partial Stop All failure/retry, and delayed Look during remove/re-add. Each passed 1/1 with no skips; the current source's atomic Stop All recovery passed 1/1 on 30 September. The runs verify that confirmed Stop/Remove state survives stale reads and relaunch, successful Stop All writes remain Off when a later write fails, and an obsolete Look cannot restore navigation. See [LOCAL-TWO-ACCOUNT-E2E.md](LOCAL-TWO-ACCOUNT-E2E.md) for the exact result bundles and fault sequence. These cases are complete; repeated-refresh stress remains untested.
- Delayed History across Stop/remove/re-add remains untested. The current isolated simulator lane cannot establish a legitimate paid Plus entitlement: its review-unlock fixture returns 503 when bypasses are disabled, and the local StoreKit configuration is not a server-verified Apple transaction. The separate History UI run proves ordinary loading and clearing after Stop, but not a held response, concurrent History screens, or a paid 30-day history window. Keep this distinct from the completed Look race.
- Interruption and device lane remains open: offline viewer → peer Stop/remove → relaunch/reconnect; sharer location permission revoked; same account used on a second physical device with Home settings changed. Simulator evidence does not prove physical convergence or background execution. Keep SMS carrier delivery, APNs token/delivery/presentation/tap, background location, and StoreKit purchase/restore/renewal/expiry/refund on the physical TestFlight acceptance list.
- The API currently publishes Look and Home-arrival notifications only. It does not push new connection requests or acceptance, so a sender whose Sharing screen stays open can see a remote acceptance only after the next scheduled refresh, a pull, or tab re-entry. Decide whether requests and acceptance need pushes. If added, use a durable, idempotent notification outbox tied to request/connection IDs so retries cannot spam or notify after cancellation/removal; avoid direct best-effort sends from retryable mutations.
- Notification route parsing maps Look to Activity and Home arrival to People, but the paired run registered no push devices. APNs transport, foreground/background/terminated presentation, permission-denied behavior, and physical delivery/tap interaction remain unverified. The API has no durable APNs outbox/retry worker; a publish attempt is not proof of delivery.

Age assurance follows the current Apple regulatory signals on supported OS versions; the Trust audience classification and jurisdiction/older-OS obligations remain unresolved. See [LOCAL-TWO-ACCOUNT-E2E.md](LOCAL-TWO-ACCOUNT-E2E.md) and [AGE-ASSURANCE.md](AGE-ASSURANCE.md) for precise limitations.
